# Валидация и метрика

Главный риск этой задачи — не переобучиться на классы, а **переобучиться на
промпты**. В train на каждый промпт есть по ответу каждой из 18 моделей;
если резать строки случайно, 17 «братьев» промпта окажутся в train, и
валидация покажет 0.9 там, где тест даст 0.35. Поэтому вся валидация
групповая.

## 1. Единица анализа — промпт

- **Сплит** режется по `prompt_id` (официальные данные) или `prompt_canon`
  (пул). Внутри промпта всегда представлены все семейства, поэтому
  групповой сплит автоматически сохраняет баланс классов.
- **Bootstrap** ресемплит промпты с возвращением, а не строки. Строки
  внутри промпта зависимы: общая тема, длина, форматирование.
- **Парный bootstrap** для сравнения двух моделей использует одни и те же
  промпты в каждом розыгрыше; так CI считается на разнице, а не на двух
  независимых BA.

Реализация: `src/ntl/metrics.py` (`prompt_scores`, `bootstrap_ba`,
`paired_bootstrap_delta`), `src/ntl/cv.py` (`group_folds`, `oof_predict`).

## 2. Канонический сплит `official_v1.json`

`splits/official_v1.json` делит 150 официальных промптов на **5 блоков по
30**. Блоки 0–3 — development, блок 4 — **sealed**. Схема использования:

| блок | роль |
|---|---|
| 4 (sealed) | не трогаем до финального отчёта; метрика один раз |
| 0–3 | development: 4-fold CV, ротация блоков |

Правила:

1. Гиперпараметры, признаки, пороги и выбор модели — только на
   development-блоках.
2. Sealed нельзя использовать для ранней остановки, выбора эпохи или
   ансамблевого веса. Если посмотрели — сплит сгорел, это нужно честно
   написать в отчёте.
3. Для сравнения с прошлыми числами допустим `splits/v2.json`
   (30 locked holdout + 120 dev, 5 повторов), но новые эксперименты
   должны идти на `official_v1.json`.

Историческая деталь: в `splits/v1.json` повторы с разными сидами давали
один и тот же набор фолдов — это был баг. `v2` исправил его случайными
фолдами; `v1` оставлен только для истории.

## 3. BA(18/prompt) и BA(2/prompt)

### BA(18/prompt)

Классическая balanced accuracy по всем строкам validation. Если каждый
промпт содержит все 18 классов, это эквивалентно среднему по промптам от
доли верных. В наших данных один промпт неполный (17 ответов), поэтому
эквивалентность приблизительная.

Плюс: стабильная метрика с малой дисперсией, удобно сравнивать модели.
Минус: **оптимистична для LB**, потому что даёт модели 18 связанных
ответов на промпт.

### BA(2/prompt)

Тест содержит примерно 2 ответа на промпт. Чтобы приблизить локальную
метрику к тесту:

1. Для каждого промпта случайно выбираем 2 ответа без возвращения.
2. Считаем balanced accuracy по получившемуся набору.
3. Повторяем 25 раз с фиксированным сидом и усредняем.

Реализация: `two_per_prompt_ba` в `kaggle/rnn/train_rnn.py`,
`two_per_prompt` в `experiments/pool_svc_baseline.py`.

Случайное угадывание: **1/18 = 0.0556**. Это точка отсчёта и для BA(18),
и для BA(2), но дисперсия у BA(2) в разы больше: на 2 ответах на промпт
одна ошибка меняет вклад промпта на 0.5.

### Почему нельзя смотреть только на BA(18)

Наши числа:

| протокол | локально | LB |
|---|---:|---:|
| 7-view стек | 0.3917 dev BA(18) | 0.356 |
| стек + kNN-центрирование | 0.4712 dev BA(18) | 0.356 |
| Gold Apex (чужой) | — | 0.662 |

Локальный 0.47 не перенёсся. Публичная абляция на форуме показала ту же
закономерность: OOF по 2 ответам на промпт коррелирует с LB на **0.91**,
по 18 ответам — на **0.13**. Поэтому основной локальный протокол для новых
моделей — BA(2/prompt), а BA(18) остаётся для сравнения с историей.

## 4. Доверительные интервалы и шум

- Bootstrap по промптам, 2 000 розыгрышей, 95% percentile CI.
- На 120 dev-промптах стандартная ошибка BA(18) ≈ **0.02**; разница
  меньше **0.015** считается шумом.
- Для BA(2) разброс выше (типично ±0.05–0.08 по розыгрышам), поэтому
  сравнивать модели нужно **парно**, на одних и тех же draw-ах, а не по
  двум независимым средним.
- Парный bootstrap возвращает Δ и CI. Если CI не содержит 0 — разница
  значима; иначе говорим «в пределах шума».

## 5. Проверки на утечки

Перед каждым экспериментом:

1. Пересечение `prompt_id` между train и validation — **ноль**.
2. Для пула — пересечение по `prompt_canon`, а не по `prompt_group`.
3. Near-duplicate промптов: косинус TF-IDF между prompt-level документами;
   пары > 0.90 разбираются вручную.
4. `max_cos_train` и `max_sim_train_prompt` у строк пула: порог 0.5,
   строки выше — в карантин.
5. Никаких признаков, посчитанных на всём train+test сразу, кроме
   transductive-методов, которые честно помечены (kNN-центрирование,
   кластеры теста). Для них важно отдельно проверять перенос.

## 6. Схема отчёта об эксперименте

Каждый результат в `docs/experiments.md` и в issue должен содержать:

- сплит и метрику (`official_v1` / `v2`, BA2 или BA18);
- число повторов/draw-ов и сид;
- среднее и CI;
- LB, если был сабмит;
- вердикт: подтверждено / опровергнуто / в пределах шума.

Без этой пятёрки число не считается результатом.
